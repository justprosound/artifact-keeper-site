:::caution[Planned feature]

:::

A protected release cannot be changed (see the [Immutability Policy](/docs/advanced/immutability-policy)). The blocklist is how you revoke one: a blocked release keeps its bytes and its coordinate, but the server stops serving it. Because a block never deletes anything, it never re-opens the coordinate for different bytes.

## Block a release

Blocking a release blocks every file of that version. Proposed endpoints:

```bash
# Block a release (reason required)
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"reason": "CVE-2026-12345: credential leak in 1.4.2"}' \
  https://artifacts.example.com/api/v1/repositories/{key}/releases/{coordinate}/block

# Lift the block
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"reason": "fixed build republished as 1.4.3; block lifted for forensics"}' \
  https://artifacts.example.com/api/v1/repositories/{key}/releases/{coordinate}/unblock
```

Blocking and unblocking need the repository `admin` action or a system administrator. Both are recorded as audit events and sent as webhooks.

While a release is blocked:

- downloading any of its files returns **403**. Authenticated callers get the block reason; anonymous callers get a plain 403 with no reason;
- it is left out of format indexes and version resolution (npm packument, PyPI simple index, Maven metadata, Helm index, OCI tag list);
- deleting it requires the [administrator override](/docs/advanced/immutability-policy#administrator-override).

## Yank instead of block

A yank is a softer block. A yanked release is hidden from "latest" and from version-range resolution, but a client that pins the exact version can still download it. Where the format has a native yank signal, the server emits it: the PEP 592 `data-yanked` attribute for PyPI, and `yanked: true` for Cargo.

A yank can be upgraded to a full block later without losing its history.

## Block a digest everywhere

A digest block refuses one piece of content wherever it appears, across all repositories. Proposed endpoint:

```bash
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"sha256": "<sha256>", "reason": "malicious payload"}' \
  https://artifacts.example.com/api/v1/admin/blocks/digest
```

A blocked digest is refused:

- on download from hosted, remote (proxy cache) and virtual repositories;
- as the source of a promotion, copy or migration;
- on every replication peer. Digest blocks replicate, and a peer applies them whatever its own repository policy.

## Incident runbook

When a published release has to be withdrawn:

1. **Block it.** Block the release in the repository it was published to, with a reason that names the incident. Clients stop receiving it at once, and the bytes stay in place for investigation.
2. **Block the digest** if the same content may exist in other repositories or remote caches.
3. **Publish a fixed version** under a new version number. The blocked version number stays burned: it cannot be reused for different bytes.
4. **Check the audit log** for the block events and for downloads of the release before the block.
5. **Decide whether to keep the block.** Leave it in place, downgrade it to a yank so that exact pins keep working, or delete the release with the administrator override if it must not be stored at all.
