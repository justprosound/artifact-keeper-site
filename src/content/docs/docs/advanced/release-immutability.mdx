Artifact Keeper refuses to replace a stored release with different bytes on its main write paths. The rules below are always on: there is no repository setting or environment variable that turns them on or off. This page describes what the server does, including the paths where the rules do not apply yet.

:::caution[Changed after v1.11.3]
This page describes the server after the release-immutability fixes that follow v1.11.3. On v1.11.3 and earlier:

- a refusal answers `409` with the code `CONFLICT`, or with a plain-text body on most native format APIs, instead of [`IMMUTABLE_RELEASE`](#the-immutable_release-error-code);
- once storage garbage collection reclaims a deleted release, its coordinate accepts any bytes;
- promotion, approval and migration can replace the bytes of a released version without the checks below;
- `?permanent=true` on delete is ignored.
:::

## The `IMMUTABLE_RELEASE` error code

Every refusal on this page answers **HTTP 409** with the stable error code `IMMUTABLE_RELEASE`. Match on the code, not on the message text: messages differ between formats and may be reworded.

On the REST API and on the native format APIs, the body is the standard error object:

```json
{"code": "IMMUTABLE_RELEASE", "message": "Artifact version already exists and is immutable"}
```

Cargo, Dart pub and Swift clients parse their own error envelope, so the code is carried inside it:

| Format | Code at | Message at |
|--------|---------|------------|
| Cargo | `errors[0].code` | `errors[0].detail` |
| Dart pub | `error.code` | `error.message` |
| Swift (`application/problem+json`) | `code` | `detail` |

One refusal does not carry the code yet: a second upload of a file that the PyPI upload API already stores answers `409` with the code `CONFLICT` (`File already exists`). Different bytes over a deleted PyPI file do carry `IMMUTABLE_RELEASE`.

Other 409 responses keep the code `CONFLICT` and are not immutability refusals: a download of an artifact held in quarantine, `?permanent=true` on an OCI repository, a repository key that is already taken, and so on.

:::note[Clients that matched `CONFLICT`]
A client or script that detected an already-published version by matching `code == "CONFLICT"` must also accept `IMMUTABLE_RELEASE`. Checking the status alone (`409`) still works, but cannot tell a refusal from a quarantine hold.
:::

## The rules

### 1. A stored path cannot be uploaded again

Uploading to a path that already holds a live artifact returns `409 IMMUTABLE_RELEASE` and keeps the stored file. This holds even when the new bytes are identical. The message depends on the format, for example:

| Format | Message on a second upload of the same path |
|--------|---------------------------------------------|
| Generic (`PUT /api/v1/repositories/{key}/artifacts/{path}`, including chunked uploads) | `Artifact version already exists and is immutable` |
| Maven release (any file outside a `-SNAPSHOT` directory, except `maven-metadata.xml`) | `Artifact already exists` |
| npm | `Version 1.2.3 of my-lib already exists` |
| Debian, RPM, Alpine package files | `Package already exists` |

The exceptions are files a format rewrites in place by design. They are listed under [What stays mutable](#what-stays-mutable).

### 2. A deleted release cannot be replaced with different bytes

Deleting an artifact leaves a tombstone (it moves to the trash). Uploading **different** bytes to a *released* coordinate after a delete returns `409 IMMUTABLE_RELEASE` with `Artifact version already exists and is immutable`. Uploading the **identical** bytes again is allowed and restores the artifact.

A coordinate counts as released when either of these holds:

- the stored artifact carried a version. On the generic upload API the version is the second segment of a path with at least three segments (`builds/v1.0.0/output.tar.gz` has version `v1.0.0`; `builds/output.tar.gz` has none);
- the format marks the path as a release file, for example a Maven release artifact, a PyPI wheel or sdist, an npm tarball, a Cargo `.crate` or a conda package.

A generic path with fewer than three segments has no version, so after a delete it can be uploaded again with different bytes.

This check runs on:

- the generic upload API (single request, multipart and chunked);
- the native uploads for Maven, npm, PyPI, NuGet, Cargo, Composer, conda and Bazel;
- promotion, bulk promotion and approval into the repository, and migration imports (see [rule 4](#4-promotion-and-migration-do-not-replace-a-release)).

Native uploads for the other formats do not run it yet; see [Known gaps](#known-gaps).

#### After storage garbage collection

Storage garbage collection permanently removes a deleted artifact from the trash once `GC_TRASH_RETENTION_DAYS` has passed (see [Environment Variables](/docs/reference/environment#scheduled-tasks)). When it reclaims a deleted artifact, it keeps a small record of the path, its version and its SHA-256 digest, but not the bytes. The record is kept for as long as the repository exists.

Rule 2 keeps applying after garbage collection: different bytes at a reclaimed released coordinate are refused for every caller, administrators included, and identical bytes are still accepted.

Coordinates that garbage collection reclaimed before the server was upgraded to a version with this record have no record, so they accept any bytes.

#### Reopening a coordinate on purpose

Only an administrator can reopen a released coordinate for different bytes, by permanently deleting it. Either of these removes the deleted artifact, and any garbage collection record for its path, at once:

- `DELETE /api/v1/repositories/{key}/artifacts/{path}?permanent=true`, which deletes and purges in one request (not available for OCI repositories);
- `DELETE /api/v1/admin/trash/{id}` for an artifact that is already in the trash (`GET /api/v1/admin/trash` lists it).

Once garbage collection has reclaimed a deleted release, there is nothing left in the trash to delete permanently. To reopen the coordinate then, the administrator must first upload the **identical** bytes again (which rule 2 accepts), and then permanently delete that artifact. Without a copy of the original bytes, the coordinate cannot be reopened.

:::caution[The window can be short]
With the defaults (`GC_TRASH_RETENTION_DAYS=0` and an hourly `GC_SCHEDULE`), a deleted artifact is reclaimable on the next garbage collection pass, so an administrator may have less than an hour to permanently delete a release from the trash. After that, reopening its coordinate needs a copy of the original bytes. Set `GC_TRASH_RETENTION_DAYS` to the number of days your administrators need.
:::

### 3. A release file can only be deleted by an administrator

`DELETE /api/v1/repositories/{key}/artifacts/{path}` returns `409 IMMUTABLE_RELEASE` with `Cannot delete an immutable/released artifact` when the caller is not an administrator and the path is a release file of its format: for example a Maven release artifact, a PyPI wheel or sdist, an npm tarball, a Cargo `.crate`, a conda package, a Debian `pool/` file, an RPM package, or an OCI blob or manifest addressed by digest. Trusted replication peers (an administrator or service-account token) are exempt so that upstream deletes can be mirrored.

Generic, NuGet, Helm and Composer paths are not release files in this sense, so anyone with the `delete` permission on the repository can delete them. Rule 2 still stops a deleted generic artifact whose path carries a version from being replaced with different bytes.

### 4. Promotion and migration do not replace a release

Rule 2 also applies when content arrives in a repository by [promotion](/docs/advanced/staging-promotion) or by migration. Identical bytes are accepted in both cases.

- **Single promotion** onto a released coordinate in the trash, with different bytes, returns `409 IMMUTABLE_RELEASE`. Nothing is copied, and the deleted artifact and its bytes stay in the trash.
- **Bulk promotion** reports the item as failed (`"promoted": false`, with a `message` that names the immutability refusal) and continues with the rest of the batch.
- **Approve and execute** returns `409 IMMUTABLE_RELEASE` and the approval stays `pending`.
- Each promotion refusal is recorded in the audit log as `PROMOTION_REFUSED`.
- **Migration** never replaces the bytes of a released artifact in the target repository, whatever its `conflict_resolution`, whether the artifact is live, in the trash, or already reclaimed by garbage collection. The item is reported as `skipped`, with a reason that starts `Release immutability conflict at <path>`, and the job carries on. See [Conflict Resolution](/docs/migration/from-nexus#conflict-resolution).

## What stays mutable

These are rewritten in place by design and are not covered by the rules above:

- **Maven snapshots**: every file under a `-SNAPSHOT` directory, and `maven-metadata.xml` and its checksums. See [Snapshot vs Release Repositories](/docs/guides/maven#snapshot-vs-release-repositories).
- **Index files**: the npm packument, the PyPI simple index, Cargo index entries, Debian `dists/` files, RPM `repomd.xml`, conda `repodata.json`.
- **OCI tags**: pushing a manifest to an existing tag moves the tag to the new manifest. Manifests and blobs addressed by digest never change. See [Docker tags](/docs/guides/docker#tags-are-mutable).
- **Conan**: recipe and package files can be re-uploaded within a revision.
- **Generic and ML-model repositories with [artifact versioning](/docs/advanced/versioning)** enabled: a re-upload appends a new revision instead of being refused.

## Known gaps

The rules are enforced on the paths named above. These paths can still change released content:

- **Native uploads for the other formats** (among them Debian, RPM, Alpine, Helm, Go, Terraform and Swift) clear a tombstone before storing the new file without rule 2, so a deleted artifact can be re-uploaded with different bytes. Rule 1 still refuses an upload while the file is stored.
- **Promotion onto a coordinate that garbage collection has already reclaimed** is not checked against the garbage collection record; promotion checks only a deleted artifact that is still in the trash.
- **Migration of OCI images** (manifests and tags) does not apply rule 2.
- **Format-native deletes** (OCI manifest delete, npm unpublish, Helm chart delete, Conan remove) do not apply rule 3.
- **The PyPI upload API** answers a second upload of a stored file with the code `CONFLICT` instead of `IMMUTABLE_RELEASE` (see [the error code](#the-immutable_release-error-code)).
